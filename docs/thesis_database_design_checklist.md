# 论文 / 留档用数据库设计模块清单

## 1. 文档定位

本文档用于支撑论文中的“数据库设计模块”章节，同时也作为项目留档材料。目标不是把当前实现包装成理想化的完全规范化数据库，而是如实说明：**本项目采用的是“工程兼容优先、平滑迁移优先的半规范化设计”**。

适用读者：
- 导师 / 答辩评审；
- 项目交接人员；
- 后续需要补写论文数据库章节的开发者本人。

---

## 2. 数据库设计目标

本项目数据库设计围绕以下目标展开：

1. **统一持久化后端**：将原本分散在 JSON / JSONL 文件中的 Profile、Event、Trace、KB 数据收敛到 MySQL；
2. **平滑迁移**：在不破坏现有接口和业务链路的前提下，支持从文件存储逐步切换到数据库存储；
3. **保留回滚能力**：通过 `file / dual / mysql` 三模式维持短期回滚与排障能力；
4. **兼容现有 payload 结构**：尽量保持与历史 JSON 结构等价，降低上层调用改动成本；
5. **为后续查询和统计打基础**：把适合拆分的结构逐步做半规范化处理，但不在当前阶段追求完全拆表。

适合论文中的推荐表述：

> 本系统数据库设计以“工程兼容优先、平滑迁移优先”为核心原则，在保证现有业务链路稳定运行的前提下，将原有文件存储逐步迁移到 MySQL，并采用主字段 + JSON 扩展字段的半规范化建模方式，以平衡结构化查询能力、历史 payload 兼容性与迁移成本。

---

## 3. 设计原则

## 3.1 工程兼容优先
- 现有业务层已经围绕历史 JSON / JSONL payload 构建；
- 因此数据库设计优先保证“**能无痛接入现有代码**”，而不是为了形式上的高范式重写所有结构；
- `repositories/*_repo_mysql.py` 负责在 ORM 行记录与旧 JSON 兼容结构之间做聚合/转换。

## 3.2 平滑迁移优先
- 通过统一 store 入口保留 `file / dual / mysql` 三模式；
- 迁移过程采用“先补数据库写能力，再做 dual，再切 mysql 默认”的 rollout 策略；
- 这意味着数据库设计必须允许一段时间内与旧文件存储并存。

## 3.3 半规范化优先于过度规范化
- 对于适合拆分、且拆分后收益明确的部分，采用子表规范化；
- 对于事件、trace 等高动态、高兼容负担数据，保留宽表与 JSON/payload 结构；
- 当前设计**不是完全 BCNF**，这是有意为之，而不是遗漏。

## 3.4 读写兼容优先于一次性收敛
- 某些表已经新增子表承接规范化字段，但旧 JSON 列仍保留并继续双写；
- 读取时优先从子表恢复，必要时回退旧 JSON 列；
- 这种设计适合论文中表述为“**兼容式半规范化演进**”。

---

## 4. 核心实体与逻辑结构

当前数据库核心实体可以概括为四组：

### 4.1 Profile 组
- `FarmerProfileORM`：农户主档案；
- `FarmerProfileEquipmentORM`：档案设备列表；
- `FarmerProfileBannedIngredientORM`：档案禁用成分列表；
- `FarmBaseORM`：基地主表；
- `FarmBaseRiskTagORM`：基地风险标签子表；
- `FarmBaseRiskItemORM`：基地风险项子表。

该组体现了“主表 + 子表 + 兼容 JSON 列”的半规范化思路：
- `farmer_profiles` 中保留主字段与约束聚合字段；
- `farm_bases` 继续作为基地主实体；
- 设备、禁用成分、基地风险标签、基地风险项已拆到子表；
- 但旧 JSON 列并未删除，用于双写与回滚。

### 4.2 Event 组
- `DiagnosisEventORM`：诊断事件宽表。

该表保留了以下特点：
- 关键筛选字段（如 `farmer_id`、`base_id`、`final_disease`、`ts`）单独建列；
- 症状、图像结果、规则结果、治疗方案、验证结果等复杂结构保留 JSON 列；
- 全量兼容 payload 保留在 `payload_json` 中。

这不是缺陷，而是当前阶段的有意设计：
- 诊断事件结构变化频繁；
- 诊断事件既用于统计，也用于审计与重放；
- 过早完全拆表会显著放大迁移成本和回归风险。

### 4.3 Trace 组
- `TraceEventORM`：多智能体 trace 事件宽表。

该表保留：
- `trace_id + seq` 顺序标识；
- 节点、状态、消息等核心字段；
- 全量 `payload_json`；
- MySQL 侧毫秒精度时间列。

当前**不继续推进 trace 的进一步拆表**，原因在于：
- trace 首要目标是链路回放与调试；
- 各节点输出结构差异大，强行拆表收益有限；
- 宽表 + payload 更符合当前“观测优先、兼容优先”的工程诉求。

### 4.4 KB 组
- `KBDiseaseORM`
- `KBTreatmentORM`
- `KBRuleORM`
- `KBSymptomMapORM`
- 以及针对 treatment / symptom_map 的规范化子表。

KB 组是当前规范化程度相对更高的一组，因为：
- 结构相对稳定；
- 后台管理和规则查询需求明确；
- 更适合做 payload 等价前提下的半规范化拆分。

## 5. 为什么采用“主字段 + JSON 扩展字段”

这是当前数据库设计中最需要在论文里解释清楚的一点。

### 5.1 原因一：历史 payload 兼容
原系统长期以 JSON / JSONL 作为权威格式。若一次性改成纯关系模型：
- 需要重写大量业务代码；
- 需要同时重写迁移脚本、回滚逻辑和测试；
- 迁移风险显著增加。

因此当前策略是：
- 把高频检索、稳定字段抽到显式列；
- 把复杂、变化快、短期不值得拆分的部分保留在 JSON 中；
- 由 repository 层负责兼容恢复旧结构。

### 5.2 原因二：降低迁移成本
对事件、trace、部分 profile/base 信息来说：
- 当前最重要的是先完成“可迁移、可切换、可回滚”；
- 而不是为了追求高范式导致迁移面过大。

### 5.3 原因三：为后续演进留接口
保留 JSON/payload 列并不意味着放弃结构化设计，而是为未来迭代预留空间：
- 当某一部分查询压力增大、结构稳定后，可以再向子表演进；
- 当前已在 profile/base 和 KB 的部分结构上采用这种渐进式方式。

适合论文中的推荐表述：

> 本系统未采用“全字段完全关系化”的数据库方案，而是结合业务稳定性、迁移成本与回滚需求，采用主字段结构化列与 JSON 扩展字段并存的半规范化建模方式。该方案能够在保证关键字段可检索、可索引的同时，保留历史 payload 兼容性，并为后续增量规范化演进预留空间。

## 6. 统一存储入口设计

当前四类数据并不是直接在业务层操作 ORM，而是通过统一 store 层封装：

- Profile：`personalization/profile_store.py`
- Event：`event_store.py`
- Trace：`trace_store.py`
- KB：`knowledge_base/kb_store.py`

统一入口设计的意义：
1. 将 `file / dual / mysql` 切换集中到一处；
2. 便于在不修改业务逻辑的前提下切换持久化后端；
3. 为数据库迁移提供统一 rollout 控制点；
4. 便于论文中描述“存储层解耦设计”。

适合论文中的推荐表述：

> 为避免数据库迁移对上层业务逻辑产生大面积侵入，本系统在 Profile、Event、Trace 与 KB 四类数据上分别引入统一存储入口，使业务层仅依赖 store 接口，而具体的数据来源可在 file、dual 与 mysql 三种模式之间切换，从而实现渐进式 rollout 与低成本回滚。

---

## 7. 迁移与切换策略

当前采用的是真实落地的 rollout 策略，而非一次性替换：

### 7.1 file
- 完全保留旧 JSON / JSONL 行为；
- 作为最保守兜底与回滚模式。

### 7.2 dual
- 读以旧文件逻辑为主（或保留兼容兜底）；
- 写同时写文件和 MySQL；
- 用于切换前后的一致性观察期。

### 7.3 mysql
- 读写都以 MySQL 为主；
- 但旧文件逻辑和迁移脚本仍保留，便于短期回滚。

这种切换方式适合论文中表述为“**分阶段迁移与运行态回滚机制**”。

## 10. 已知限制

当前数据库设计仍存在以下边界，这些内容应在论文中明确写出，而不是回避：

1. **不是完全规范化数据库**：当前是半规范化、工程优先设计；
2. **`diagnosis_events` 仍是宽表 + `payload_json`**：这是为了兼容诊断链路审计、历史回放和字段演进；
3. **`trace_events` 仍是宽表 + `payload_json`**：这是为了支持多节点 trace 回放与调试，而不是为了报表型分析；
4. **部分 repository 仍采用 delete + 全量重写策略**：优先保证幂等与兼容性，后续再考虑增量 upsert；
5. **旧 JSON / JSONL 文件仍保留**：用于 dual/file 模式、短期回滚、历史对账和迁移复核；
6. **不是所有 JSON 列都已经继续拆表**：这属于后续优化方向，而非当前阶段目标。

---

## 11. 后续优化方向

后续如果论文中需要写“可继续改进方向”，建议使用以下真实表述：

1. 结合真实查询负载，进一步优化 `diagnosis_events` 与 `trace_events` 的索引设计；
2. 对部分高频查询场景探索数据库端聚合，减少 Python 全量遍历；
3. 在确认回滚窗口结束后，再评估是否继续缩减 file/dual 兼容逻辑；
4. 对 KB 与 Profile 的部分全量重写逻辑尝试演进为更细粒度 upsert；
5. 根据长期运行情况，再评估是否需要继续拆分某些 JSON 字段。

强调：
- 当前**不计划继续拆 `diagnosis_events` / `trace_events`**；
- 这不是技术缺陷，而是基于当前业务需求、调试需求与工程投入做出的阶段性设计取舍。

## 12. 可直接用于论文撰写的推荐表述

### 12.1 关于整体设计
> 本系统数据库设计采用工程兼容优先、平滑迁移优先的半规范化方案。对于稳定且高频检索的字段，采用显式关系字段建模；对于结构复杂、变化频繁或需要保留历史 payload 兼容性的部分，采用 JSON 扩展字段保底，并由 repository 层负责与旧数据结构之间的等价转换。

### 12.2 关于迁移策略
> 在数据库迁移过程中，系统并未直接废弃原有文件存储，而是通过统一存储入口保留 file、dual、mysql 三种运行模式，实现了从文件存储到 MySQL 的渐进式切换与短期运行态回滚。

### 12.3 关于 Event / Trace 宽表设计
> `diagnosis_events` 与 `trace_events` 继续保留宽表与 payload 字段，并非数据库设计不完整，而是基于诊断链路审计、trace 回放、字段演进频率和迁移成本综合考虑后的阶段性工程选择。

### 12.4 关于半规范化
> 本项目数据库设计并不追求一次性达到完全高范式，而是在不破坏现有业务接口的前提下，通过“主表 + 子表 + JSON 扩展字段”的方式逐步提升结构化程度，以实现可迁移、可部署、可验证、可回滚的工程目标。
